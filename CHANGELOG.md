# Changelog

All notable changes are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed
- **README banner as bricks.** Each block of the banner's letters is now a brick with a stud, and the bricks drop into place when the page loads and build again every 15 seconds (CSS only, no script); with reduced motion set, the finished banner is shown. Generated by `tools/make_assets.py` like before. The app itself is unchanged.
- **The window is drawn as bricks.** Buttons are bricks with studs on top, a lit top edge and a shaded bottom edge; cards are square plates with a row of studs; switches are a small plate with a 1x1 brick that moves from one end to the other; the progress bar fills with bricks; text fields are set into the surface; the wordmark, the sidebar markers and the library tiles are bricks with studs, like the README banner. Colours, text, layout, keyboard focus rings and the contrast checks are unchanged. The window now prefers the Exo 2 font (SIL Open Font License) when it is installed, and otherwise uses the same fonts as before. Checked by screenshots under Xvfb and the existing window tests;
- **After a run, the result reads as a result.** Its first line is a bold headline and the details below it are plain text; the progress line says the run has ended instead of keeping the last percentage and time left; after an unpack, the checklist marks it done ("Done: the files are in ...") instead of a red cross for the existing destination, and the bar says how to unpack again (another prefix) in grey instead of amber;
- **Smoother wheel scrolling.** A turn of the mouse wheel now glides the page 80 pixels and slows to a stop, instead of jumping about a third of the page at once; turning the wheel the other way stops the glide, and moving with Tab still brings the focused control into view at once. Checked under Xvfb by a window test; not tried on a real mouse or touchpad.

### Added
- **A menu bar and view settings.** File (choose installer, new prefix, settings, quit), View (text size, reduce motion, remember window size) and Help (keys, about), with keys for each. The view settings are also in a new Window card in Settings and are kept in `~/.config/gitfurl/view.json` (mode 0600; only these settings, written when one changes). Help > Keys lists niri's own keys on niri, where the window cannot maximize or minimize itself. Checked under Xvfb by window tests and screenshots; not on a real desktop.

### Fixed
- **The window is named gitfurl, not Tk.** The window now has the class gitfurl (WM_CLASS "gitfurl", "Gitfurl") instead of Tk's default "Tk", and the desktop entry from `gitfurl cli desktop-entry` says `StartupWMClass=Gitfurl`, so a dock or task bar can match the window to the entry and show its name and icon. Checked under Xvfb (xprop and a window test); not checked on a real desktop;
- **A test that failed by chance.** The test that checks only one log is read counted every file opened in the whole process, so a thread left from another test could make it fail (it did once, in CI on main). It now counts only the opens made on its own thread.

## [1.4.0] - 2026-11-26
A native route: when an installer's payload is FreeArc archives gitfurl can read, gitfurl unpacks them itself instead of running Setup, chooses that route on its own and says why, on the command line and in the window. Also an Inno Setup reader for the plan, `gitfurl cli extract-inno`, Stop for the window's Create now, `prefix create --runtime proton` and an optional menu entry. Tested with unit tests, synthetic installers, and archives and setups built in the sandbox; compatibility with any particular third-party installer is still unverified.

### Added
- **Stop for the window's Create now.** While Create now builds a prefix, Stop is shown and, after its own confirmation, ends wineboot's process group and, with Wine, asks that prefix's Wine server to exit (with Proton the dialog says Proton's own server and container may keep running); the folder is kept and marked incomplete, and the prefix list shows it as "incomplete". Tested by driving the real buttons under Xvfb with a stand-in for wineboot; not run with a real Wine or Proton.
- **`prefix create --runtime proton`.** `gitfurl cli prefix create` takes `--runtime` and `--proton-path` like `install`, so a prefix for Proton installs can be created on its own: it runs `umu-run wineboot --init` with `PROTONPATH` and `GAMEID=umu-0`, and the plan names the Steam Linux Runtime download umu-run may make on its first run. `--wine-addons` with Proton is refused. Tested with unit tests (fake `umu-run`); not run with a real Proton.
- **Optional menu entry.** `gitfurl cli desktop-entry` adds gitfurl to the desktop's application menu after an approval that shows the plan: a `gitfurl.desktop` file and a copy of the icon in the user's own data folder. The plan lists the folders it creates and the exact `Exec` line. `--remove` takes both files away (and gitfurl's own leftover temporary files), and leaves the folders; files gitfurl did not write are left as they are, and a link in place of either file is refused. Tested with unit tests in temporary folders, and the generated entries pass `desktop-file-validate`; not checked in a desktop's menu.
- **Free space against what the archives unpack to.** On the Setup route, when FreeArc archives beside the installer can be read, the preflight (dry run and approval, command line and window) now says what they unpack to, from their own indexes, as a lower bound for the install, and warns when free space is smaller. Only archives that belong to the installer count (the route's link test), so unrelated archives in a downloads folder are left out. Before, it compared free space only with the size of the installer's folder. It stays advice; the native route already stops when the files do not fit. Tested with unit tests and archives built by the tests (the command line's dry run; the approval text on the command line and in the window uses the same call but was not tested); not run under Wine.
- **Stall notes name the newest window.** With stall advice on, gitfurl looks at the run's windows at each progress sample (one `xwininfo` call, `xprop` only for new windows) and the stall note names the window that opened most recently after the run's first windows, with when it opened: usually the dialog that is waiting. The stall note now comes once per quiet period instead of once per run. `--stall-after` no longer makes the automatic choice take the Wine route; on the native route it is listed as not applying, as in the window. The window now always gives Setup runs stall advice (120 s), and a crash or stall note stays in the status text until the run ends. Tested with unit tests and fakes for the window tools; not run under Wine.
- **Native route in the window.** The window picks the route like `gitfurl cli install` without `--route`: when the installer's payload is FreeArc archives gitfurl can read, Setup is not run and gitfurl unpacks them itself. A switch, "Run Setup instead (Wine/Proton route)" (off by default), and the Setup-only options choose Setup. One approval shows the whole plan. The command line's stop checks are shown instead of the approval when one applies. Stop works during the ClamAV scan, the prefix creation and the unpack. A ClamAV match asks a second time. The end text has the unpack's result and the local log. The checklist no longer asks for Wine when the native route needs none. The window now refuses to run as root anywhere (both routes and Create prefix). Tested with unit tests and the real window under Xvfb with a synthetic installer; not run under Wine.
- **Crashes and stuck windows during a Setup run.** While Setup runs under Wine, gitfurl notices Wine's crash handler (`winedbg.exe`) starting in the prefix. It prints one note, writes a log line and a `crash_handler` event, and adds a `Crash:` line to the end text. A crash handler that was running before the run is not counted. When the stall advisory fires, or on a crash, the note lists the titles of the windows the prefix's programs have open (read with `xwininfo` and `xprop` when they are installed and a display is set; not in portable runs). It is advice only: gitfurl never answers, closes or stops anything. The progress monitor (`/proc` reads every interval) now runs on every Setup run, also without `--progress`, because that is how a crash is noticed. Tested with unit tests (fake `/proc`, fake `xwininfo` and `xprop`); see docs/testing.md for the Wine run.
- **Native route: archives the setup script names.** The automatic choice of `gitfurl cli install` now also links the FreeArc archives to an Inno Setup installer when its setup script names every one of them (external `[Files]` sources and `[Code]` strings, with the numbered files after a named one), so archives whose names share nothing with the installer can go native. The name check stays as the fallback. The route line says how the archives were linked, or how many the script names and which it does not, and with `--route native` it says when they were not linked. The route line also now lists 4x4 and srep among the methods. Tested with unit tests on synthetic setups built by the tests.
- **Inno Setup: slice files and setup-0.bin.** gitfurl's Inno Setup reader now also reads setups whose file data is in slice files beside the installer (disk spanning: `setup-1.bin`, `setup-2.bin`, or `setup-1a.bin`, `setup-1b.bin` with several slices per disk) and setups built without Inno's loader, whose setup data is in `setup-0.bin` beside setup.exe and whose file data is in slice files even without spanning. The names follow the installer's own file name, letter case ignored, and only the installer's own folder is searched. The plan and the detection show where the data is ("setup data in setup-0.bin beside the installer") and list the slice files the setup names, present or missing. `gitfurl cli extract-inno` now extracts from them: before anything is written each slice file it needs is opened without following links and its header (the signature of the setup's format, and a size equal to the file's real size) is checked, and each chunk must start with its marker and end in exactly the slice file its location names; chunks that run on from one slice into the next are read across. A missing, short or wrong slice file is refused with the reason; one that changes during the run ends the extraction with an error, and a swapped slice is caught by the chunk's decompression or the file's checksum (the file is removed again). Password-protected and encrypted setups are still refused. Written from a clean-room behaviour specification. Checked on 2026-11-23, in the sandbox, against 18 setups built with Inno Setup 6.3.3, 6.7.4 and 7.1.1 (spanning, three slices per disk, no loader with and without spanning, solid and not): every file matched its source; other data formats follow the specification only.
- **Code map** (`docs/code-map.md`): diagrams of the layers, module imports, the install flows on both routes and in the window, the native route's data flow, entry points, where files go, and which tests and CI jobs cover each module. `docs/architecture.md` now also describes `unattended.py`, `procgroup.py`, `safety.py` and `__main__.py`.
- **Native-first route for `gitfurl cli install`.** gitfurl now picks the route itself and says why in the dry run and before the approval (`route: native (chosen by gitfurl)` or `route: wine (chosen by gitfurl)`, with the reasons). It is native when the installer is Inno Setup (or itself a FreeArc archive) and every FreeArc archive beside it reads cleanly, uses only storing, lzma, exe, delta, rep, 4x4 (lzma inside) and srep, and holds only safe names. On the native route Setup is not run at all: Wine only creates the prefix when asked, gitfurl unpacks the archives into `C:\Games\PREFIX` with all the checks of `gitfurl cli extract`, and then lists program candidates and redistributable installers it found, without running them. The plan says word for word what is skipped (Setup's own files, shortcuts, registry entries, redistributables, every step of its script), shows every step, and one approval covers them. The unpack writes a local log (mode 0600), an optional event log, `[progress] native unpack:` lines, and exits 0, 1 or 130. Otherwise the route is Wine/Proton with the reason (for example an archive whose checksums do not match, or a method gitfurl does not handle). `--route native|wine` overrides the choice; `--route native` refuses, with nothing run, when the native route is not possible. The automatic choice is native only when the archives are linked to the installer by name (one shared base name that is the installer's name or part of its folder's name) and no option that only a Setup run uses (`--unattended`, `--portable`, `--wine-debug`, `--show-changes`, `--runtime proton`) was given; otherwise it is Wine with the reason. A prefix created on the native route gets `WINEDLLOVERRIDES=mscoree,mshtml=` for wineboot only (no Mono or Gecko dialogs) and an incomplete-marker until wineboot succeeds; a marked prefix is refused. Before the approval the run checks free space (including room for a prefix still to be created) and compares the decoders' memory with free memory (`--no-memory-limit` skips that check); the dry run lists every reason a real run would stop. A Ctrl-C after the unpack reports the unpack's result instead of "nothing was written". At first the window kept running Setup; it now takes the native route too (see "Native route in the window" above). Tested with unit tests on synthetic files only (a fake Inno Setup file and archives built by the tests); the native unpack has not been run in the sandbox, and the Wine dialog override has not been run at all.
- **Inno Setup reader (read-only) in the plan.** For an Inno Setup installer the plan now reads the setup's own data with gitfurl's own reader (`gitfurl/inno.py`, written from a clean-room format specification): the offset table, the format ID, both header blocks (CRC-32 checked) and every entry list. It shows the data format, the app name and default folder, the privileges and compression, what Inno itself writes (files stored in setup.exe, external files, folders, shortcuts, INI values, registry entries), the `[Run]` entries a silent install would run in order with how each waits, which of them look like redistributables (listed as skipped by gitfurl's own extraction; Setup itself would still run them), whether Setup asks for a password, encrypted files and disk spanning. Data formats 5.5.0 to 7.1.1 (Unicode) are read; the ANSI edition of Inno Setup 5, development and unofficial format IDs, and fully encrypted setups are refused with the reason. Formats 5.5.7, 6.3.0, 6.7.0 and 7.1.1 and a modified 5.5.0 layout were checked against real setups; the others follow the specification only and the plan says so. The route choice itself is unchanged (see the native-first route above).
- **Archive-name preflight.** The plan lists the files the setup names beside itself (`{src}\...` in external `[Files]` entries and in the string constants of the compiled `[Code]`, found by a read-only scan; the code is never run) and checks them against the installer's folder and up to two folder levels below it, case ignored (a symbolic link counts as present when it leads to a file; deeper names are listed as not checked). A missing one gives a warning that a silent run is likely to stop on the script's own error window. Names the script builds at run time are not seen.
- **Inno Setup extraction, command line only.** `gitfurl cli extract-inno INSTALLER --prefix NAME [--dry-run] [--yes]` writes the files Inno Setup itself holds for `{app}` to `C:\Games\NAME` in an existing prefix, without running the installer: stored, zlib, bzip2, LZMA and LZMA2 data, solid or not, with the x86 call filter undone. It follows the default setup type, components and checked tasks and the first language; temporary helpers, files outside `{app}`, external and downloaded files, the uninstaller, redistributables and entries that depend on a `[Code]` check are listed as skipped. Refused before anything is written: a password-protected setup, encrypted files, a compression method gitfurl does not handle, unsafe or Windows-unusable names, a name that is both a file and a folder, an LZMA dictionary over 1 GiB, files that overlap in one chunk, or no file to write. The plan shows the bytes decoded and thrown away to reach later files in a solid chunk. Each file's SHA-1 or SHA-256 is checked; a file that does not match, or that Stop or an error cut short, is removed again.
- **FreeArc extraction: 4x4 and srep.** `gitfurl cli extract` now also decodes `4x4` with `lzma` inside (the data cut into pieces compressed separately, as in FreeArc's multi-threaded presets such as `rep+exe+delta+4x4:lzma`) and `srep` (long-range matches, the external compressor many installers register in their `arc.ini`; also under the names `srep64`, `srep_new` and `srep_old`), alone or chained with the methods before. All four srep stream formats are read, with every block checksum srep writes (md5, sha1, sha512, VMAC, SipHash, or none, checked per block), with or without the one-byte header FreeArc may add. The decoders are gitfurl's own, written in a clean room from behaviour-only specifications. srep blocks are capped at 8 MiB (or the method's `b` size, at most 64 MiB), and what srep keeps between blocks is capped at twice the block's files' size (at least 16 MiB, at most 1 GiB); the plan's memory line includes it and a note states it, and data that needs more is refused with an error. `4x4` around any other method, and `srep` with `index=`, stay "a method gitfurl does not handle". Tested with the specifications' vectors and the tests' own encoders, and on 2026-11-20 (UTC) against 47 archives made in the sandbox with seb3773/freearc-c and srep 3.93a (built from its public source) and 49 standalone srep streams: every file matched. Not tested with archives written by the original FreeArc or third-party installers.

- **FreeArc inspection (read-only).** When the installer, or a large file beside it, starts with the FreeArc signature, the plan now reads that archive's own index and checks its CRC-32 values. It shows the file and folder count, the total size, how many data blocks use storing, lzma or "a method gitfurl does not handle", the self-extracting stub size, the locked flag and names that would not be safe to extract. A readable index makes the detection "likely"; otherwise it stays "possible" and the plan says why. The inspection itself extracts nothing and does not choose the route (see the native-first route above). Tested with archives built in memory by the tests, and checked read-only against 15 archives made in the sandbox with seb3773/freearc-c; not yet against archives written by the original FreeArc.

- **FreeArc extraction: exe, delta and rep, and chains.** `gitfurl cli extract` now also decodes data blocks whose method is `exe` (x86 branch filter), `delta` (binary tables) or `rep` (long repeats), alone or chained with `storing` and `lzma` (for example `rep+exe+delta+lzma`, at most 8 methods), with gitfurl's own streaming decoders written from behaviour-only specifications. The plan and the archive summary name the supported methods and chains by gitfurl's own names; any other method is still shown only as "a method gitfurl does not handle". Every buffer is capped before a block is read (the lzma dictionary, rep window and delta block at 1 GiB each), and the plan's memory line adds up the caps of one block's methods. Damaged data, or data that asks for more than the caps, ends the extraction with an error; files already written are kept. Data that gives little or no output for its size (many empty delta blocks in a row, rep headers and match tables far larger than the output) is refused as damaged, and Stop is checked while it is read. A block whose stream is longer than its files is decoded only as far as the files need. Tested with streams and archives built by the tests' own encoders and the specifications' test vectors, and on 2026-11-19 against 20 archives made in the sandbox with seb3773/freearc-c: the 15 using these methods were extracted byte for byte, the 5 using other methods were refused. Not tested with archives written by the original FreeArc.

- **FreeArc extraction (storing and lzma), command line only.** `gitfurl cli extract INSTALLER --prefix NAME` writes the files of the FreeArc archives beside the installer to `C:\Games\NAME` in an existing prefix, with gitfurl's own reader. The installer is not run, so nothing of its own steps happens; the result is "files extracted", not "installed". A plan and an approval come first (`--dry-run` shows it). Encryption and every method other than storing or a single lzma are refused before anything is written, as are unsafe or clashing names, names Windows cannot use (trailing dot or space, `<>:"|?*`, device names), more than 1,000,000 folders, an existing destination and too little space or inodes; folders that differ only in letter case become one folder, as on Windows. Files are created new, never overwrite anything, are not written outside the destination, and are CRC-checked. Tested with archives built by the tests and with 8 storing/lzma archives made in the sandbox with seb3773/freearc-c; not with archives written by the original FreeArc.

### Fixed
- **No host `wineserver -k` after stopping a Proton wineboot.** When gitfurl stopped `umu-run wineboot` (Stop, Ctrl-C or a timeout), it then ran the system's `wineserver -k` against the Proton prefix, a different Wine build from Proton's own. It now skips that step for Proton, as the installer's Stop already did, and says so in the notes. Unit-tested with dummy processes.
- **A prefix whose creation did not finish is no longer used on the Setup route.** The incomplete marker was only checked on the native route; a Setup run now refuses such a prefix before anything starts, and the window shows it as "incomplete" with Run off. Unit-tested.
- **Stall notes list only windows a user can answer.** In a sandbox run with a synthetic Inno Setup installer waiting at its language dialog, the stall note listed Inno's hidden loader and application windows (2 and 1 pixel high) beside the dialog, and named no window, because the dialog was already open at gitfurl's first look. Windows smaller than 8 pixels either way, and windows that are not mapped (`xwininfo -id`), are now left out; when no window opened after the first look and several are listed, the note names the window on top, and a single window is simply listed. `xwininfo` lists the topmost window first, not last as #37 assumed, so its caps now keep the topmost windows. Tested with unit tests and sandbox runs with that installer (the final code at 17:17 UTC; the sentence for several windows is unit-tested only); not run in the window.
- **ClamAV database not seen with ClamAV 1.5.** `clamscan --version` on ClamAV 1.5.4 reads no database, so `gitfurl cli doctor` and the scan approval said "no signature database" although scans loaded one. gitfurl now asks `clamscan --version` first and, when it names no database, asks `clamconf` for the database folder and runs `clamscan --database=FOLDER --version` (both bounded, read-only probes). Tested with fake scripts and with ClamAV 1.5.4 on this machine (the doctor line only; no scan was run).
- **Stop during prefix creation on the Setup route.** In the window, Stop while the prefix was being created waited for wineboot to finish (up to 300 s) on the Setup route, while the native route ended it at once. Both routes now end wineboot's process group and report the run as cancelled; the prefix folder is kept and marked incomplete. The native plan now says when the Mono and Gecko switch is on but not used. The user guide no longer says Ctrl-C leaves wineboot running on the command line (it has ended wineboot's group since 2026-11-16). Tested with unit tests; not run under Wine.
- **`gitfurl cli doctor` wording.** tkinter now reads "available (importable)" instead of "available at importable". The "optional" notes for bwrap (new: for `--portable`), umu-run and innoextract now show whether the tool is found or not. clamscan's line starts with the ClamAV version ("clamscan: ClamAV 1.5.4 at ...") instead of "clamscan: at ...".
- **A stopped unattended run was reported as "the installation succeeded".** Inno Setup writes its "Installation process succeeded." line after its own file list, before steps the setup script runs afterwards. The end text, the window and the run log now say "The run was cancelled, so Setup did not finish." for a stopped run, and describe the line as covering only Setup's own file list; the `unattended_result` event gains `cancelled`.
- **A possible fatal error at exit after Ctrl-C with `--progress`.** The progress monitor and the memory limit's adjuster now stop under a lock, so no progress line or note is printed after they stop and a final sample never runs at the same time as the thread's; the result is flushed before gitfurl exits.
- The plan no longer says "native extraction is not available in this version"; the route line gives the real choice.

### Changed
- **Native route internals, for the window.** The checks that stop a native run before it starts are one function (`route.native_stops`) used by `gitfurl cli install`, whose output and exit codes are unchanged. New: `route.perform_native` (one approved native run on a worker thread), `route.NativeControl` (Stop for it), progress numbers from `run_native`, and a Stop for prefix creation from another thread (`prefixes.run_in_group(should_stop=...)`; the stopped prefix keeps its incomplete marker). The window uses them (see Added). Tested with unit tests on synthetic archives and fakes, and a real process group for the stop.
- **Prefixes gitfurl creates no longer wait on Wine's Mono and Gecko dialogs.** On the Wine route too (`install --create-prefix`, `gitfurl cli prefix create`), `wineboot` now runs with `WINEDLLOVERRIDES=mscoree,mshtml=` for that command only, as the native route already did, and the plan says so. Creating a prefix then needs no answer and Wine downloads nothing; the prefix has no Mono (.NET) or Gecko, which most installers do not need. `--wine-addons` keeps Wine's dialogs; in the window, so does the switch "Let Wine offer Mono and Gecko when it creates a prefix" (off by default), for Run and Create now. Proton prefixes are not changed. Before, creating a prefix in the sandbox stopped at Wine's Mono dialog (no network to answer it), a likely cause of the 300 s wineboot timeout seen there on 2026-11-16 (not confirmed for that run). Tested with unit tests (fakes for wineboot); not run under Wine.
- **FreeArc extraction removes a file that fails its CRC-32 check** and names it, as `extract-inno` already does with its checksums, so no damaged file is left in the prefix looking complete. If it cannot be removed, the result names it as damaged and still there. A file cut short by Stop is still kept and named as incomplete.
- FreeArc names: `\` now counts as a folder separator, like `/`, so names from an archive made on Windows are no longer counted as unsafe for that alone.

## [1.3.0] - 2026-11-18
An unattended install for Inno Setup installers, and the first runs of Wine with an installer under the memory limit (an installer built for the test, in the sandbox). Compatibility with any particular third-party installer is still unverified.

### Added
- **Unattended install for Inno Setup installers** (`gitfurl cli install --unattended`, and the window option "Install without the installer's windows (Inno Setup only)"), off by default. When the read-only check finds an Inno Setup ID, gitfurl starts the installer with Inno Setup's documented switches (`/SP- /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /DIR=C:\Games\PREFIX /LOG=...`): no wizard and no installer windows, every choice at the script's default. The installer still unpacks its own files under Wine. Afterwards gitfurl reads the log Inno Setup wrote in the prefix and reports the exit status's meaning, whether the log says the installation succeeded, how many files it lists, error lines, and whether the install folder exists. Refused, with nothing run, for installers without an Inno Setup ID. Tested with mocks and with one Inno Setup 7.1.1 installer built for the test, under Wine in the sandbox; not with third-party installers.

### Documentation
- Memory limit: the first run with Wine and an installer (the test installer above, in the sandbox inside a scope with the limits). Over the hard limit with swap available, the run was slowed down and moved to swap, not stopped, and the install finished.
- README: a Community section with the gitfurl forum on the undecuple Discord server, and a "Questions and discussion" link on the new-issue page.

### Project
- Published releases are now announced in the gitfurl forum on Discord, one thread per release, by a GitHub workflow (no change to gitfurl itself, which still makes no network requests).

## [1.2.1] - 2026-11-17
A fix to the memory limit's end text and wording. Checked against systemd 262 with test programs and a stand-in for Wine; still never run with Wine, Proton or a real installer.

### Fixed
- Memory limit: after a normal run the end text no longer says that an out-of-memory stop "could not be checked". systemd removes a scope that ended normally before gitfurl can read it; a scope ended by the out-of-memory killer stays as failed. gitfurl now passes `OOMPolicy=stop` explicitly and, when the scope is gone and was not seen failed, says that no out-of-memory stop was recorded, and why. Checked against systemd 262 with test programs (no Wine, no installer).
- Memory limit wording: at the hard limit the kernel stops a process of the run and systemd then ends the whole run (it was described as stopping processes only).

## [1.2.0] - 2026-11-17
An optional ClamAV scan before a run, and a memory limit for the run that is on by default. Neither was tried with Wine, Proton or a real installer: both were tested with stand-ins, and the memory limit also with test programs in a real systemd scope.

### Added
- An optional **ClamAV scan** before a run (`gitfurl cli install --scan`, and a toggle in the app), off by default. It runs the `clamscan` already on PATH on the installer and the regular files directly beside it, in its own process group with a timeout (`--scan-timeout`, default 600 s), only after approval. gitfurl passes no option that changes files (never `--remove`, `--move` or `--copy`); `clamscan` may still write its own temporary files. A match stops the run with nothing run or created, naming the files and signatures and saying that false positives are common for game installers; `--allow-scan-hit` or a second dialog in the app (default No) overrides it. A scan error, a timeout or unreadable output always stops the run and can not be overridden; a match in a scan where some files could not be scanned or read is such an error. gitfurl never runs `freshclam` or updates the database; `doctor` and the approval show the database date and warn when it is older than 7 days. A real `clamscan` was never run: this was tested with a stand-in script only.
- A **memory limit**, on by default (`--no-memory-limit` and the window option "Limit memory (reduces the chance of running out)" turn it off). The run's command, including `bwrap` for a portable install and `umu-run` for Proton, is started with `systemd-run --user --scope` with `MemoryMax` = `MemAvailable` minus a reserve of `max(1 GiB, 10% of MemTotal)` and `MemoryHigh` = 90% of that; it refuses to start below a 1 GiB hard limit and says how much memory to free. While the run lasts, the soft limit is lowered when other programs need memory and raised back later (only on that one unit, through `systemctl --user set-property --runtime`). After the run, an out-of-memory stop inside the scope is reported. It reduces the chance that the system runs out of memory; it does not guarantee that the installer succeeds. If systemd-run, a user manager or the memory controller is missing, the plan says why and a run needs the option turned off. `doctor` reports whether it is available. `wineboot` during `install --create-prefix` gets the same limits. **Visible change:** on a system without a user systemd manager or without the memory controller delegated to it, runs are refused until the limit is turned off. Swap is not limited, and programs already running outside the scope (for example a Wine server left from an earlier run) are not covered. Tested with fakes and test programs in a real scope only: Wine, Proton and installers were never run under the limit.

## [1.1.0] - 2026-11-17
The second release: Stop for a running installer, cleanup when prefix creation times out or is interrupted, a read-only guess at the installer's format, a reworked window (footer, keyboard use, checklist, banner, resizing), an optional portable install inside bubblewrap, and run events. As with 1.0.0, it does not mean any particular installer works: compatibility is unverified, a complete install has not been tested, and the code has not been audited.

### Added
- A **Stop** button (and Ctrl-C on the command line) for a running installer. It signals only the run's own process group (SIGTERM, then SIGKILL after 10 s), then, for Wine, asks that prefix's Wine server to exit. The run is reported as cancelled (exit status 130, a `cancelled` event); the log is kept and nothing is deleted. Complete process-tree termination is not guaranteed, and stopping through `umu-run` is unverified.
- A read-only, advisory preflight before a run: measured free space, installer-folder size and memory, apart from estimates; required space is shown as unknown and no multiplier is applied.
- The progress line shows how many processes run in the prefix, their CPU use and helper names, with a "quiet" hint; `doctor` reports CPU threads and available memory.

- A footer on every page: whether Wine and umu-run were found, the keys that work on the page, and the run state (Idle, Creating prefix, Installer running, Stopping...).
- Keyboard use: an orange focus outline on every button, switch, choice, prefix card and sidebar item; Tab follows the screen order and scrolls the page to the focused item; Enter or Space activates; Up and Down move between prefixes in the Library; Esc goes from a prefix's page back to the Library. There is no screen-reader support.
- A prefix's page has a checklist (installer chosen, Wine or umu-run found, prefix exists or will be created, each with a tick or cross and a sentence) and a bar at the bottom with Stop, Create now and Run installer that stays in view, with the reason in words when a button is off.
- The "Wine was not found" message is a banner with a Check again button, on the Library and on a prefix's page.
- An optional **portable install** (`gitfurl cli install --portable`, and a toggle in the app), off by default. The Wine installer runs inside bubblewrap with the dedicated prefix, a temporary home and `/tmp`, the run's log file and `/dev/dri` writable, the network off, the environment cleared except an allowlist (so tokens and keys are not passed), your home folder and the D-Bus sockets hidden and Wine's menu builder disabled. Whatever the installer leaves in the prefix runs again outside the sandbox when the prefix is used later. It reduces changes outside the prefix as far as bwrap isolates them; it is not a guarantee or a security boundary. It refuses (no fallback) without `bwrap`, with the proton runtime and as root.
- Optional, advisory inactivity detection (`--stall-after SECONDS`, `RunOptions.stall_after_s`; off by default): one `possibly_stalled` event and one note if no payload read, no CPU use and no log growth for that long. It never stops or signals anything.
- With the detailed log and the progress monitor, `processes` and `memory` events (program names, count, `MemAvailable`); no environment values.
- A run now returns a result with `started`, `extraction_observed` and `exit_status` as separate fields (also in the last event and in the end text). `extraction_observed` is a heuristic ("observed activity": the prefix grew and payload files were read); it does not show that anything was extracted or installed. The old `(status, log)` unpacking still works. Tested with fakes only, not with Wine or a real installer.

### Changed
- Before a run, the plan preview, the approval dialog and `gitfurl cli install --dry-run` show a read-only guess at the installer's format (Inno Setup, FreeArc), from file headers only. Nothing is extracted and the route is always Wine/Proton; `doctor` also notes whether `innoextract` is on PATH by running its `--version` (a bounded probe, as for `wine`); nothing runs it to extract.
- The content follows the window width (the window already had a smallest size of 900 x 620) and nothing is clipped at that size; one spacing scale, one type scale, one corner radius, and a computed contrast check of every text colour (disabled buttons and the hover colour of the ghost button were below 4.5:1 and were changed).
- Run is now off, with the reason shown, when Wine (or umu-run) is not on PATH or when the prefix does not exist and creating it is off. Before, the button was on and a dialog said so after the click. The dialogs remain as a second check. Approvals, dry runs, Stop and cleanup are unchanged.
- The README, the user guide and SECURITY.md state exactly what the progress display reads from `/proc`, including the process environment (only to find the prefix).

## [1.0.0] - 2026-11-16
The first release. It means the app, the command line and the safety checks are complete for the stated scope. It does not mean any particular installer works; compatibility is unverified, and the single-file Linux build is not proven on every desktop (see the README known issues).

### Added (after review)
- `release.yml`: builds the graphical app as one Linux program on a `v*` tag and attaches it, with SHA256SUMS, to a draft release. Not yet run.
- `Dockerfile`, `compose.yaml`, `docs/docker.md`: a container with the network off and a read-only installer folder. Builds and starts under Podman.
- Refusal to create prefixes or run installers as root.
- `doctor` reports tkinter.
- `docs/testing.md`, Python 3.11 and 3.12 in CI, shellcheck, a check for tracked installers and large files, and dependabot for the action pins.

### Changed (after review)
- The sidebar shows the real reason when umu-run cannot be probed, and the README screenshot is retaken with nothing missing or failing.
- `WINE*` variables inherited from your shell are no longer passed to the installer.
- Cleanup `folder` mode refuses `~/Downloads`, `~/Desktop`, `~/Documents` and similar general folders.
- `tools/sandbox.sh` exits with a clear message outside NixOS.
- Docs say what "never touches `~/.wine`" does and does not cover, and that the sandbox wrapper is NixOS-only.


### Added
- Optional guess at the installed program (`--find-exe`; a switch in the app). Local only: it runs nothing and touches no launcher.
- Proton as a runtime choice (`--runtime proton --proton-path DIR`; a control in the app), through umu-run. It needs a Proton folder you already have and downloads nothing itself. `doctor` now reports umu-run.
- Progress reporting (payload read, rate, rough ETA, bytes written to the prefix) in the app and with `--progress`. Optional detailed JSON event log (`--detailed-log`) and `--wine-debug`.
- A user guide: `docs/user-guide.md`.
- The app was redesigned with rounded cards, a sidebar of pages and block-letter tiles, to match the repository assets.
- Optional cleanup of the original installer (`--cleanup installer|folder`; a dropdown in the app). Off by default. Nothing is deleted unless the installer exits with status 0, the list of files is shown for approval first, symlinks are removed and never followed, and it refuses home, the root, mount points, system folders, folders holding gitfurl's own data, and folders with more than 200 entries.
- Optional report of what the installer changed (`--show-changes`; a checkbox in the app). It compares before and after snapshots of the prefix (files and registry key names) and of a few host places an installer could touch outside the prefix (menu entries, autostart, the home folder's top level). It lists names only, never contents, and is best effort.
- "Create it if it does not exist" option for the prefix, on by default in the app. The confirmation dialog says the prefix will be created first. On the command line it is opt-in: `--create-prefix`. If the prefix cannot be created, the installer is not run.
- Graphical app (tkinter), now the default: `gitfurl` opens it. It shows the environment, previews the plan, creates prefixes and runs installers, each after a confirmation dialog.
- The app uses a library and detail layout in the style of Bottles: a sidebar of prefixes, then cards for the installer, options and plan.
- `tools/sandbox.sh`: no network, empty home, host session variables unset; `SANDBOX_ETC=1` adds the read-only files umu and Proton need.
- The command line moved behind `gitfurl cli ...`. A bare `gitfurl cli doctor` no longer runs the CLI.
- Banner, app icon, favicon and social preview in `assets/`, generated by `tools/make_assets.py`.
- `gitfurl cli doctor`: reports the platform, Wine and bubblewrap, with a timeout on each probe.
- `gitfurl cli install FILE --dry-run`: shows the command, prefix, working directory and environment overrides. Runs and creates nothing.
- `gitfurl cli prefix create NAME` and `prefix list`: dedicated prefixes under the per-user data directory, created only after approval.
- `gitfurl cli install FILE --prefix NAME`: runs the installer after approval, writes a local log (mode 0600) and reports the exit status.
- Mock-based tests; no test needs Wine, a network or a real installer.
