# Testing

What has been run, and how to repeat it. Counts are not listed here because they go stale; run the commands.

## Unit tests (no Wine, no installer, no network)
    nix develop -c python3 -m pytest -q      # or: PYTHONPATH=src python -m pytest -q
    ruff check .

They use temporary folders, fake `/proc` data, fake Wine and mocked subprocess calls. One test opens the window under Xvfb for 5 seconds; it is skipped when `xvfb-run` or tkinter is missing. CI runs both commands on Python 3.11 and 3.12.

## Window polish (footer, keys, focus, checklist, resizing)
`tests/test_gui_polish.py`. Pure functions are tested directly: WCAG contrast of every text colour pair the window uses against 4.5:1 (and the focus outline against 3:1), the checklist and the reasons shown for a disabled button, the footer texts. The window tests start gitfurl under `xvfb-run -a` in a subprocess, with a temporary home, a fake Wine path and no network, and drive it through `gitfurl.gui.main(driver=...)`: Up/Down/Enter in the Library, Esc from a prefix's page, Space and Return on a switch, an orange outline on every custom widget kind when focused (and gone when not), Tab order matching the screen order on a prefix's page (and no keyboard trap), the footer on every page and its run state, the Wine banner, the checklist and the Run and Create states, the sticky bar, no horizontal clipping at 900 x 620, mouse-wheel scrolling, scroll-into-view on focus, and the content following a larger window. They pump `root.update()` until a condition holds (with a cap) rather than sleeping. They are skipped when `xvfb-run` or tkinter is missing.

Not tested: a real display or window manager (Xvfb has none, so the minimum size is checked as the value set, not as enforced by a window manager), HiDPI or scaling, other fonts or themes, Wayland, a screen reader (Tk offers none), pointer hover and drag, and what the screen looks like (contrast is computed from the colours, not measured on screenshots). Clicking Run, Create or Stop through the window is still not tested.

## Starting a real installer (manual, not in CI)
This was done with the maintainer's explicit approval, for two specific files the maintainer supplied and confirmed in person. The limits: this machine only, inside `tools/sandbox.sh` (no network, empty home), no credentials present, only counts and the exit status looked at, nothing copied off the machine, and no installer path or name in any tracked file or message. Anyone else repeating this should use their own installers under the same limits.

Checked by hand on 2026-11-16, Linux x86_64, Wine 11.0 (nixpkgs `wineWow64Packages.stable`):
1. Make a work folder on a disk with space. It will hold the prefix.
2. Run `tools/sandbox.sh INSTALLER_DIR WORKDIR sh script.sh`, where the script starts Xvfb and then `python -m gitfurl cli install /installer/setup.exe --prefix t --create-prefix --yes`. The wrapper has no network and an empty home. It is NixOS-only.
3. Count the windows (`xwininfo -root -tree`) and note whether the process is still running every 15 seconds. Stop it after 120 seconds.
4. Delete the work folder.

Stop only what you started: run the sandbox in its own process group (`setsid`, then `kill -- -PGID`), never by process name, and use `xvfb-run -a` rather than a fixed display, so other people's Wine, Proton or Xvfb jobs on the same machine are never touched.

Result: two user-supplied installers started and stayed open for the whole 120 seconds. Only counts and the exit status were looked at. No installation was completed, and nothing was run afterwards. The installers are not published or named here, and none is in the repository. Do not copy installer output, screenshots or logs off the machine.

One installer was also started through Proton (GE-Proton) with umu-launcher in the same sandbox, with `SANDBOX_ETC=1`. It stayed open for 120 seconds. Proton's output held one error line whose source was not found.

## Stop and preflight
Tested with controlled dummy processes (a Python script that starts a child and a grandchild) and fake `/proc` and meminfo data, plus a fake `wineserver` script that only records its arguments. They cover: the whole group ending on Stop, a child that ignores SIGTERM being killed after the grace period, a program that moved to another session surviving (the documented limit), stopping twice or after the end doing nothing, only the recorded group and `wineserver -k` for the plan's prefix being signalled (no call by name), Ctrl-C, the `cancelled` event, a failing installer reported as failed, and the preflight labels and caps. None of this shows that any real installer stops or installs correctly. The GUI's real `stop_clicked` is driven by `tests/test_gui_stop.py` (see "Stop button in the window" below); `stop_applies` is also tested as a plain function. The CLI cancel test replaces `run_tracked` with a fake that performs a real stop before anything started, so it covers stop-before-start only; the stop of a running group is covered by the `StopTests` above. The CI-pinned tool versions (`pytest==8.3.5`, `ruff==0.11.13`) have not been run; the checks above used the nix dev shell's newer versions.

Observed once by hand on 2026-11-16 (Wine 11.0 wow64, NixOS, a throwaway prefix, the built-in command `cmd /c ping -n 60 127.0.0.1`): the run's own processes shared the leader's process group, and Wine's server and services each had their own session, so a group stop ended the run and left the prefix's server running; `wineserver -k` for that prefix then ended the rest. Not observed: a stop during `wineboot`, or an installer attached to a Wine server that was already running.

Not shown: Stop through `umu-run`. The attempt in `tools/sandbox.sh` with the cached Proton failed before starting ("umu has not been setup for the user; an internet connection is required"), so the Proton behaviour is unverified.

## Stop button in the window
`tests/test_gui_stop.py` runs `tests/gui_stop_driver.py` under `xvfb-run -a` (skipped when `xvfb-run` or tkinter is missing), one fresh process per case. The driver calls the real `gitfurl.gui.main()`; only its edges are replaced: tkinter's `mainloop` (the case runs instead), the message boxes and file dialog, and `run_tracked` (a fake that waits for an event the test controls; no process, no Wine). The real Run button, `run_clicked`, `stop_clicked`, `poll`, `start_busy`/`end_busy` and the Stop button's click handler run. HOME and the XDG folders are a temporary folder, and `wine` is a fake script that prints a version. No source change was needed to reach the closure. Cases:
- Yes: the run's control is cancelled, the button is disabled, the status says "Stopping the installer...", and the run ends as "Cancelled."
- No: nothing changes (not cancelled, button enabled, status unchanged).
- The run ends while the dialog is open, then Yes: the result text is left alone, nothing is cancelled, and the next run's Stop is visible and enabled. Removing the second `stop_applies` check from `stop_clicked` makes this case fail (tried once by hand).
Not covered there: a real process group being stopped from the window (that is `StopTests`), the real modal dialog's look or keyboard handling, Proton's wording of the dialog, the Cancel path of a failed run, and the 10-second grace period from the window. Run 6 times in a row on 2026-11-16 with the nix dev shell's pytest and ruff (newer than the CI pins), all passed; each case takes about 4 seconds.

## Stop against a generated test installer (2026-11-16)
The maintainer pointed at a generated test installer: an Inno Setup 5.5.0 `setup.exe` (4 MB) and two `.bin` files (3.8 GB) beside it, made for testing. Only header bytes were read; the `.bat` and the checksum tool beside it were never run. Run once, in `tools/sandbox.sh` (no network, empty home), Xvfb, Wine 11.0 wow64 from nixpkgs, branch `fix/stop-races`:
- `gitfurl cli install ... --create-prefix` did not get past creating the prefix: `wineboot --init` was still running after 300 s (`control.exe` and `rundll32.exe` were running; the cause was not confirmed), then gitfurl ended with an uncaught `subprocess.TimeoutExpired` (now a clear error message, tested with a fake runner only). A Ctrl-C during that step ended gitfurl with 130 in 1 s and left `wineboot`, `services.exe` and other Wine processes running. That leftover is not fixed; the hang itself is not explained.
- Cause of the hang, observed once afterwards in the same sandbox with plain `wine wineboot --init` and `xwininfo`: windows titled "Wine Mono Installer" (`control.exe`) and "rundll32" were open and waiting, with no network to fetch Mono. So `wineboot` was waiting for a dialog nobody could answer. gitfurl does not change this: setting `WINEDLLOVERRIDES=mscoree,mshtml=d` avoids the prompt but also means no Mono or Gecko in the prefix, which could affect .NET and browser-component installers, so it is left to the maintainer.
- With the prefix made by hand first (`wine wineboot --init`, `WINEDLLOVERRIDES=mscoree,mshtml=d`, exit 0), the installer started (`setup.exe`, `setup.tmp`) and stayed open for 60 s with 0 bytes of the `.bin` files read. One Ctrl-C sent to the gitfurl process: it exited 130 after 1.0 s, the event log ends with `cancelled` (no `exit`), the note says the prefix's Wine server was asked to exit, and no Wine process was left in the sandbox.
- Not shown: a complete install, Stop at other phases, Proton, more than one run.

## Prefix creation timeout and Ctrl-C (2026-11-16)
`tests/` cover `run_in_group` with dummy processes and a fake `wineserver` that only records its arguments: a normal exit signals nothing; a timeout ends the leader and its child (a child that ignores TERM is killed even when the leader already exited on TERM) and runs `wineserver -k` with this prefix's `WINEPREFIX`; Ctrl-C does the same and re-raises; only the leader's group is signalled and `os.kill` is never called; a missing `wineserver` does not hide the timeout; `install --create-prefix` prints the same notes and exits 130 for an interrupt during prefix creation (with the prefix step faked). The hand run above predates the rewrite of the cleanup and was not repeated. Checked once by hand in `tools/sandbox.sh` (Wine 11.0, no network): `gitfurl cli prefix create` while `wineboot` waited on the Mono dialog, one Ctrl-C after 25 s: gitfurl ended with status 130 within 1 s and no Wine process was left (before this change `wineboot`, `services.exe` and others stayed). A second Ctrl-C during the cleanup is held back and only shortens the grace wait (tested with real SIGINTs sent to the test process itself); the notes in the error say what was really done, including a failing or missing `wineserver`, and the final wait for the first process is capped at 10 s. `wineserver` is taken only from an absolute path (beside an absolute `wine`, or an absolute PATH result). Not checked: the graphical app's prefix creation, and Proton.

## Memory limit (2026-11-17)
`tests/test_memlimit.py` uses a fake `systemd-run` and a fake `systemctl` on a temporary PATH (both record their arguments; the fake `systemd-run` execs the command after `--`, as the real `--scope` mode does, so the command keeps the process and group gitfurl started), fake `/proc/meminfo` data, a fake runtime folder and a fake cgroup tree with a fake `memory.events`. It covers: the budget (reserve `max(1 GiB, 10%)`, hard and soft limit, refusal below the 1 GiB floor with the numbers and how much to free), the adjustment rule (lowered by the shortfall from the run's usage, clamped at the floor, raised by the surplus, never above the start value, small changes skipped), the adjustment calls naming only the one unit and never `MemoryMax`, a failing `set-property` noted once, the thread stopping, the availability reasons (no `systemd-run`, no `XDG_RUNTIME_DIR`, no user manager socket, no cgroup v2, no memory controller), the exact wrapped argv, an old `systemd-run` refusing a `$` in the command, `execute` wrapping the wine argv, the bwrap argv (portable) and `umu-run` (proton), `wineboot` wrapped in its own unit during `--create-prefix`, Stop and a real Ctrl-C (SIGINT sent to the test process itself) ending a run through the fake scope with status 130, `oom_kill` from `memory.events` and `Result=oom-kill` reported in plain words and the failed unit cleared, refusals that run and create nothing, `--no-memory-limit` leaving the argv unchanged, the CLI's exit status 2 and hint, the dry run and the approval showing the values without starting a process, `doctor`'s line, and the window (under `xvfb-run -a`, skipped without it): the option on by default, Run off with the reason when the limit is unavailable, and on again once the option is turned off. The existing CLI tests pass `--no-memory-limit`, the window checklist test turns the option off, and the Stop driver reports the limit as available, so they do not depend on the machine's systemd. The whole suite was also run once with `XDG_RUNTIME_DIR` unset (the limit unavailable) and passed.

Checked by hand on 2026-11-17, on one NixOS machine (systemd 262, kernel 7.3, cgroup v2, zram and a swap file), with test programs only (no Wine, no Proton, no installer):
- `user@1000.service` showed `Delegate=yes` and `DelegateControllers=cpu memory pids`; its `cgroup.controllers` and `app.slice`'s `cgroup.subtree_control` listed `memory`.
- Without `--expand-environment=no`, `systemd-run --scope` replaced `$$` in the command line with `$` (its default expansion); with it, the text was passed unchanged.
- The command run through `systemd-run --user --scope` had the same process id and process group as the process started by Python; a child that called `setsid` was in the same scope cgroup. `systemctl --user set-property --runtime <unit> MemoryHigh=100000000` changed `MemoryHigh` and left `MemoryMax` alone.
- A Python program allocating 400 MiB in 10 MiB steps, `MemoryHigh=150M MemoryMax=200M`, swap not limited: it finished in 2.3 s with status 0; the scope's `memory.current` stayed at about 152 MiB (the rest went to swap), `memory.events` showed `high 26` and `oom_kill 0`.
- The same with `MemorySwapMax=0` added (not what gitfurl sets): it stalled at about 160 MiB for about 170 s (`high` rose to about 6700, `oom_kill 0`) and was then ended by a TERM to its own process group.
- `MemoryMax=200M MemorySwapMax=0` without a soft limit: the kernel killed it at about 190 MiB (status -9) within 1 s. With `--collect` the unit was gone at once and reads of `memory.events` every 50 ms never saw the kill; without `--collect` the unit stayed `failed` with `Result=oom-kill` and the journal line "The kernel OOM killer killed some processes in this unit", and `reset-failed` unloaded it. That is why gitfurl does not pass `--collect`. A successful scope without `--collect` was unloaded a moment after it ended.
- gitfurl's own `execute` with the limit on and a fake `wine` script (it printed `/proc/self/cgroup`) against the real systemd: the script ran in `app.slice/gitfurl-realcheck-...scope`, the log and events had the values, the end text said no out-of-memory stop was seen, and the unit was unloaded afterwards.
Only the test programs started for these checks were stopped, by their own process group. Not tested: Wine, Proton or an installer under the limit; the soft limit being lowered or raised against the real systemd (only the fake); an out-of-memory stop through gitfurl's own code (only with the test program and plain `systemd-run`); the window's Create now and `cli prefix create` (not wrapped); other distributions, systemd versions under 254 (the `$` refusal is tested with a fake only), and the CI-pinned tool versions (`pytest==8.3.5`, `ruff==0.11.13` were not run; the dev shell's newer versions were).

Checked by hand later on 2026-11-17 (same machine, systemd 262; test programs only), with `systemd-run --user --scope -p MemoryMax=200M -p MemorySwapMax=0`, reading `systemctl --user show -p LoadState -p ActiveState -p Result -p OOMPolicy` at 0, 0.2, 1 and 3 s after `systemd-run` returned:
- `true`: exit 0; `LoadState=not-found` at once (the unit was already gone).
- A program allocating up to 600 MiB: exit -9; `LoadState=loaded ActiveState=failed Result=oom-kill OOMPolicy=stop` at every read.
- A parent that would exit 0, or 3, after its allocating child: the child was killed, systemd ended the parent (`systemd-run` exit -15), and the unit stayed `failed` with `Result=oom-kill` at every read.
- With `MemoryHigh=180M` as well, the same children slowed down for over 120 s before the kill; the unit still ended as `failed`, `Result=oom-kill`.
- A run of gitfurl's own window (stand-in `wine`, limit on, real systemd) that ended normally showed "memory.events could not be read after the run", the reason for the change above.
Each failed test unit was then cleared with `systemctl --user reset-failed <that unit>`. After the change, the same window run (stand-in `wine`, limit on, real systemd 262) passed `-p OOMPolicy=stop`, which systemd accepted for the scope, ended with status 0, and the end text said "no out-of-memory stop was recorded in this run"; no unit was left. Not tested: an out-of-memory stop through gitfurl's own code against the real systemd (its hard limit here is about 17 GiB and swap is not limited, so a test program spills to swap instead), systemd versions other than 262 (whether older ones accept `OOMPolicy=` for a scope was not checked), and a `DefaultOOMPolicy=` other than the default.

## Unattended Inno Setup, and Wine under a memory limit (2026-11-17)
`tests/test_unattended.py` covers, with synthetic files and a mocked launcher: the switches and paths built for an Inno Setup ID, refusal without one and for a bad prefix name, the switches following the installer in the command, the option off by default, the dry run showing everything and running nothing, refusal before anything runs, a run reading a synthetic Inno log (success, a missing log, error lines cleaned and capped at five, only the last 4 MiB read, invalid UTF-8), Inno Setup's exit-status meanings, and the window's plan text with the option on and off.

Checked by hand on 2026-11-17, on one NixOS machine (Wine 11.0, systemd 262, Xvfb), with an installer built for the test and nothing else:
- The installer: Inno Setup 7.1.1 (`innosetup-7.1.1-x64.exe` from the project's GitHub release, sha256 checked against the release's published digest), installed with its own silent switches in a throwaway prefix inside `tools/sandbox.sh` (no network), compiling a 40-line script of ours. It copies two files of random bytes (1,500 MiB and 300 MiB) from beside `setup.exe` at install time (Inno's `external` files, read while installing, as large repacks do) and, if a `memtest.txt` beside it holds N, keeps N MiB of memory in use during the install. Neither the installer nor its payload is in the repository.
- Each run: `tools/sandbox.sh` (no network) started inside `systemd-run --user --scope -p MemoryHigh -p MemoryMax -p OOMPolicy=stop`, with `gitfurl cli install --portable --unattended --progress --no-memory-limit` inside (the sandbox hides the user systemd manager, so gitfurl's own limit cannot run inside it; the scope was started from outside with the values given).
- Run A, gitfurl's computed limits (about 16.8 GB soft, 18.6 GB hard), no memory held: no installer window; exit status 0; the end text said Inno Setup's log reports success with 2 files and that the install folder exists; both installed files were byte-identical to the payload. The scope's memory reached about 5.2 GB, mostly page cache from the copy. No `high` or `max` events.
- Run B, 2 GiB hard limit, 3,000 MiB held: the installer's script failed with a runtime error at about 1.6 GB (the setup program is 32-bit), below the limit. The end text gave exit status 3 with its meaning and quoted the error lines from Inno's log; the install folder did not exist.
- Run C, 1 GiB hard limit (0.9 GiB soft), 1,500 MiB held: the run was not stopped. The scope's memory stayed at about 0.96 GB, 1.66 GB went to swap, `memory.events` showed `high` about 9,200, `max 0`, `oom_kill 0`, and the install finished with status 0. Progress lines showed the payload being read at 80 to 100 MB/s.
- In each run the unit ended `LoadState=not-found` (`Result=success`) and no Wine process was left. The work folders were deleted afterwards.

## The single-file build (release workflow)
`release.yml` builds one Linux program with PyInstaller. Checked on 2026-11-16 by running the workflow by hand (it builds and uploads only):
- The checksum file matches. `cli --version` prints the release version (1.0.0 for that build) and `cli doctor` runs. The 1.1.0, 1.2.0 and 1.2.1 builds have not been checked this way yet.
- The window opens (stays open 6 s under a virtual display) in CI and in a Debian image that has Tk and fonts.
- On a bare Debian with no fonts it loads its bundled Tk but cannot create a window; the app now prints that reason.
- On NixOS it stops with `libxcb.so.1: cannot open shared object file`, because the build expects the system's standard X11 libraries.
Not proven: Fedora, Arch, Wayland-only sessions, older distributions than Ubuntu 22.04.
